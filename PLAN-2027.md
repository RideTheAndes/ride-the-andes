## Phase 1 — Spanish URLs + `hreflang` *(highest value, do first)* · **DONE 2026-08-23**

> Implemented ahead of the October trigger at the operator's request — the work was
> agent-executed, so it cost none of the attention the parking clause protects.
> `tools/build-es.mjs` generates `es/index.html`; the missing-key guardrail below is
> enforced (the generator fails loudly) and the CI assertion runs as `build-es --check`
> in `.github/workflows/main.yml`. The original spec, for context:

**The problem.** `index.html` is bilingual only at runtime: `setLang()` swaps `innerHTML` from the `ES` dictionary in `site.js`. The server never delivers Spanish HTML at any distinct URL. Google indexes one English page. The site is **structurally unable to rank for Spanish-language queries** — `cicloturismo Boyacá`, `tours en bicicleta Colombia`, `gran fondo Boyacá inscripción`.

That matters more here than for most operators: the Gran Fondo Boyacá Mundial itself draws ~2,000 riders, overwhelmingly Colombian and Spanish-speaking. The nearest, warmest audience is the one the site cannot currently reach.

**Why it's ready.** Translation coverage is **100%** — 333 keys used, 334 in `ES`, 0 unresolved (verified 2026-08-09). The Spanish copy already exists and is operator-written. This is a *plumbing* job, not a translation job.

**Approach.** Generate `/es/index.html` as a real static page from the `ES` dictionary, at build or by script, then:

- reciprocal `hreflang="en"` / `hreflang="es"` / `hreflang="x-default"` on both versions
- `<link rel="canonical">` self-referencing on each
- both in `sitemap.xml`
- the EN/ES toggle becomes a *link* between two URLs, not a JS swap (keep the JS path as a fallback)
- `_redirects` must not shadow `/es/` — rules are first-match-wins, check ordering

**Non-negotiable guardrail.** The generator must **fail loudly on a missing key**, never silently emit the English fallback. Add a CI assertion that `keys(index.html) ⊆ keys(ES)`. Without it, a future missing key ships a half-English "Spanish" page and nobody notices — which is exactly the failure mode a review already hallucinated once.

**Effort:** 1–2 days including QA. **Netlify preview required** (touches `index.html`).

**Do not** add `hreflang` before the URLs exist. Pointing `hreflang` at the same URL twice is invalid and worse than nothing.

## Phase 2 — Make the photography indexable

**The problem, measured on current main:**

| Metric | Count |
|---|---|
| `<img>` tags across the whole site | **1** |
| …with non-empty `alt` | **0** |
| CSS background images | **47** |

Google Images does not index CSS `background-image`. The strongest asset this business has — the Boyacá photography — earns essentially zero image-search traffic, and image search is a real discovery channel for "where should I ride" travel intent.

**Approach.** Convert the highest-value background photos to real `<img>` with descriptive `alt`: the six stage cards, the four POI cards, the five hotel cards. Fifteen images, chosen because each already has a hand-written `aria-label` from the accessibility pass that can seed the `alt` text.

**The hard part is CSS, not HTML.** The current `.slot` pattern layers a gradient overlay via `::before`/`::after` and positions text over the image; that assumes a `<div>` with a background, not a replaced element. Each component needs reworking with `object-fit` and a wrapper, then visual QA at every breakpoint. This is why it wasn't done in the earlier audits — it cannot be done blind without risking the design.

**Explicitly out of scope:** the hero rotation frames. Those are decorative and stay `alt=""` — inactive frames are hidden with `opacity:0` only, so all three sit in the accessibility tree simultaneously and per-frame `alt` would announce three descriptions for one visual slot. That decision is documented in `index.html` and `site.js`; don't reverse it.

**Also:** add `<image:image>` entries to `sitemap.xml` once real `<img>` tags exist.

**Effort:** 2–3 days with careful visual QA.

## Phase 3 — Content that answers real traveller intent

Six journal articles are live. The two with the clearest search intent and lowest competition are already published:

- *Cycling at Altitude in Colombia: How to Acclimatise*
- *Is It Safe to Cycle in Colombia? An Honest Local Answer*

**Next, in priority order** — these are topic suggestions; the operator must verify every fact before publishing, none of it is asserted here as true:

1. **Visa & entry requirements for Colombia** by likely source market (US, Canada, UK, EU, Australia). High-intent, evergreen, and it removes a genuine booking objection.
2. **Flying with a bike to Colombia** — airline policies, case options, what happens at BOG. Extremely high commercial intent; almost nobody covers the Colombian specifics.
3. **What a Gran Fondo actually is**, for the rider who's never done a mass-participation event. Feeds the race-week departures directly.
4. **Training plan for a 10-day tour at altitude** — the query that reaches riders 4–6 months out, i.e. exactly the booking lead time.

One article a month, properly researched, beats six thin ones. Each should link to `/index.html#route` and the dossier CTA.
